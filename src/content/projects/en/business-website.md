## Context and problem

A small business needs to explain its services, its approach and what a visitor can do next. Forma & Grão turns that problem into a personal project: an **entirely fictional** furniture, restoration and interior-planning workshop.

The aim was a complete, verifiable journey from discovering services to preparing a request. This is not commissioned work and does not represent a trading business, clients or commercial results.

## Solution and visitor journey

The application has four pages: home, services, about and contact. The homepage introduces the proposition and approach; service descriptions explain each offering; the about page identifies the fictional nature of the business.

The contact page completes the journey with a practical workflow that needs no backend: **prepare, review and download a TXT request**. The interface explains that nothing is sent to the workshop and recommends sample data. Service links preselect the relevant form option.

## Implemented features

- Navigation across four pages and a 404 response for unknown addresses.
- Validation of name, email, service and description, including empty fields and length boundaries.
- Field-associated errors, a focusable error summary and accessible status messages.
- A text preview and actual UTF-8 download; subsequent edits invalidate the preview to prevent exporting an outdated version.
- Field clearing and `textContent` rendering, without interpreting entered HTML.
- Responsive layout, visible focus, a WebP hero image and an SVG illustration on the about page, with alternative text and explicit dimensions.

## Architecture and technical choices

Semantic HTML is generated by JavaScript modules sharing navigation, footer and presentation components. Service content is separate from rendering. Validation and request-summary creation form a pure module reused by the tests.

Native Node.js tools generate static files and serve the preview. There are no npm dependencies, remote fonts or UI libraries. This keeps execution straightforward and makes the implemented behaviour explicit. No application server was added merely to imitate a commercial contact flow.

## Tests and validation

**12 automated tests passed.** The suite covers validation, boundaries, normalisation, the summary, routes, assets, anchors, accessible structure and local-server behaviour.

The application's verification record also documents form/download checks, keyboard use and four viewport widths. The captures show the homepage and services page of the published demonstration. Technical tests and visual inspection do not constitute user research or a complete accessibility audit.

## Limitations and availability

There is no email delivery, backend, ordering, quoting or persistent storage. The request stays on the page until clearing or reloading; only a downloaded file remains on the device. The application is PT-PT only. The live demo and source code are available through the links at the start of this case study.

## Learning and next steps

The central decision was to align the interface promise with the system's actual capability: a local file is demonstrable functionality; an unsupported “message sent” confirmation would not be. Separating content, rendering and validation makes that journey easier to test.

English translation and screen-reader checks are possible next steps. A backend would require real delivery, privacy and server-validation requirements; it is not part of the implementation.
